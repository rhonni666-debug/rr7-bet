============================================================
1. VISÃO GERAL
============================================================

RR7
- É o operador/plataforma que mostra jogos para o usuário final.
- Hoje é o primeiro cliente de homologação da RIPCOM.
- Possui usuários, área administrativa, catálogo, wallet DEMO e infraestrutura de testes.
- A futura wallet de dinheiro real pertence ao operador RR7, não à RIPCOM.

RIPCOM
- É a provedora de jogos independente.
- Não deve ser confundida com o operador RR7.
- Pode fornecer jogos para RR7 e, futuramente, para outras plataformas.
- Possui API B2B própria, player próprio, autenticação de operador, catálogo por parceiro, sessões, rounds, releases e telemetria.

ECLIPSE SERPENT
- Primeiro jogo autoral oficial da RIPCOM.
- Código: ripcom-slot:eclipse-serpent
- Estado atual: SANDBOX / DEMO.
- Possui runtime server-side e interface independente RIPCOM.
- O operador não precisa receber o código-fonte do jogo para integrar.

ARQUITETURA RESUMIDA
Plataforma parceira -> RIPCOM API -> sessão -> RIPCOM Player -> motor do jogo -> wallet/callback do operador.

4. RIPCOM B2B API v1
============================================================

FUNÇÃO:
supabase/functions/ripcom-b2b/index.ts

STATUS:
ACTIVE
Versão implantada no Supabase: v2 da Edge Function.

AUTENTICAÇÃO:
Cada operador usa um par RSA.
- Chave privada: fica SOMENTE com o operador.
- Chave pública: cadastrada na RIPCOM.

HEADERS B2B:
X-Ripcom-Operator
X-Ripcom-Timestamp
X-Ripcom-Request-Id
X-Ripcom-Signature

CANONICAL STRING:
METHOD\nPATH\nTIMESTAMP\nREQUEST_ID\nSHA256_HEX(BODY)

ASSINATURA:
RSA-SHA256 / RSASSA-PKCS1-v1_5.

ENDPOINTS PRINCIPAIS:

GET /v1/health
- Verifica se a API está online.

GET /v1/games
- Retorna apenas jogos autorizados para aquele operador.

POST /v1/sessions
- Cria sessão de jogador para um jogo autorizado.

POST /v1/games/launch
- Gera URL de abertura do player RIPCOM.
- Novos launches apontam diretamente para o player independente RIPCOM.

POST /v1/sessions/close
- Encerra uma sessão.

PLAYER STATE
- Operação interna do player para carregar sessão, jogo, símbolos e saldo DEMO.

PLAYER SPIN
- Executa uma rodada no servidor.
- O resultado não é calculado no navegador.

PLAYER CLOSE
- Fecha sessão pelo player.

IDEMPOTÊNCIA:
X-Ripcom-Request-Id identifica cada request B2B.
Repetir o mesmo ID com request diferente gera conflito.

6. OPERADORES B2B RIPCOM

Cadastro das plataformas que podem consumir a RIPCOM.

CAMPOS IMPORTANTES:

- wallet_mode: DEMO ou EXTERNAL_CALLBACK.
- callback_url: endpoint do operador para wallet callbacks.
- max_requests_per_minute: rate limit.
- max_sessions_per_minute: limite de criação de sessões.
- revoked_at: revogação.
- last_key_rotation_at: controle de rotação de chave.

21. REGRA REGULATÓRIA BRASIL — IMPORTANTE
============================================================

CNPJ sozinho não autoriza uma plataforma a oferecer apostas/jogos on-line com dinheiro real no Brasil.

Segundo a Secretaria de Prêmios e Apostas do Ministério da Fazenda, para operar apostas de quota fixa nacionalmente é necessária autorização prévia da SPA/MF. Desde 01/01/2025, apenas empresas autorizadas podem operar nacionalmente.

Também segundo o Ministério da Fazenda, os aportes do apostador devem ocorrer por transferência eletrônica entre uma conta cadastrada do apostador e a conta do agente operador. Valores recebidos de conta não cadastrada devem ser devolvidos.

Fontes oficiais para consulta:
- Ministério da Fazenda — Apostas de Quota Fixa

============================================================
22. POR QUE NÃO USAR UMA CONTA BANCÁRIA COMUM DIRETAMENTE
============================================================

Uma chave PIX ou conta PJ comum digitada no site não substitui uma integração de pagamento regulada.

O desenho correto é:
Jogador -> PSP/instituição de pagamento -> validação de titularidade -> conta transacional do operador -> webhook PSP -> payment_intent -> ledger BRL.

Benefícios:
- idempotência;
- conciliação;
- devolução automática quando necessária;
- prevenção de crédito duplicado;
- trilha de auditoria;
- KYC/titularidade;
- separação entre saldo e settlement;
- menor exposição de dados bancários.

23. SEQUÊNCIA CORRETA PARA ATIVAR DINHEIRO REAL FUTURAMENTE
============================================================

1. Preencher em /admin/ripcom-empresa os dados reais da empresa/CNPJ.
2. Validar qual entidade será juridicamente o agente operador RR7.
3. Obter/confirmar autorização regulatória aplicável.
4. Cadastrar a referência da autorização no sistema.
5. Contratar PSP/instituição de pagamento compatível com operação autorizada.
6. Criar merchant/account no PSP para o CNPJ correto.
7. Cadastrar somente referências públicas/IDs no banco; segredos ficam em secrets do backend.
8. Integrar webhook assinado do PSP.
9. Implementar criação de depósito via PSP, nunca via chave PIX fixa exposta.
10. Implementar KYC/idade/titularidade.
11. Implementar confirmação atômica no ledger.
12. Implementar saque com validação de titularidade.
13. Implementar reconciliação financeira.
14. Testar PSP_SANDBOX.
15. Fazer revisão de segurança/compliance.
16. Somente então marcar READY_FOR_AUTHORIZED_PRODUCTION.
17. Ativar PRODUCTION_ENABLED apenas quando todos os guards estiverem satisfeitos.

30. PRINCÍPIO DE ARQUITETURA QUE NÃO DEVE SER QUEBRADO
============================================================

RIPCOM = PROVEDORA DE JOGOS.
RR7 = OPERADOR.

A conta bancária/PSP do RR7 não deve ser incorporada dentro da RIPCOM como se fizesse parte do jogo.

Isso permite que futuramente:
RR7 -> RIPCOM
Operador B -> RIPCOM
Operador C -> RIPCOM

Cada operador mantém sua própria wallet, compliance, PSP e relacionamento financeiro com seus jogadores.
A RIPCOM fornece jogo, sessão, resultado e protocolo B2B.
