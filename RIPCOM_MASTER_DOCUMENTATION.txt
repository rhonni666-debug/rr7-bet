======================================================================
1. O QUE É A RIPCOM
======================================================================

RIPCOM é a provedora própria de jogos criada para não depender de provedores externos para os jogos autorais.

A ideia central é separar três coisas:

1) RIPCOM = provedora dos jogos.
2) RR7 = primeira plataforma/operadora que consome a RIPCOM.
3) Jogos RIPCOM = produtos independentes que futuramente podem ser oferecidos para outras plataformas.

A RIPCOM não deve ser tratada como um jogo interno do RR7. Ela foi estruturada para possuir API B2B, operadores independentes, autenticação própria, catálogo por parceiro, sessões próprias e player próprio.

======================================================================
2. COMO ESTAMOS DESENVOLVENDO SEM DEPENDER DE CRÉDITOS
======================================================================

O desenvolvimento segue o mesmo princípio usado no app do gêmeo digital:

- GitHub é a fonte de verdade do código.
- Supabase é usado como backend, PostgreSQL e Edge Functions.
- Lovable é opcional e não é necessário para continuar o desenvolvimento.
- Alterações são feitas diretamente no repositório.
- GitHub Actions executa testes, TypeScript e build.
- Cada bloco é construído de forma incremental para evitar reconstrução do projeto inteiro.

Isso significa que falta de créditos em construtor visual não bloqueia o desenvolvimento da RIPCOM.

3. ARQUITETURA GERAL
======================================================================

Fluxo atual:

PLATAFORMA PARCEIRA
        |
        | API B2B assinada RSA
        v
RIPCOM B2B API
        |
        | valida operador / jogo / sessão
        v
RIPCOM GAME RUNTIME
        |
        | motor do jogo / RNG / rodada
        v
PLAYER RIPCOM
        |
        v
JOGADOR

O RR7 é atualmente o primeiro operador sandbox.

Fluxo do RR7:

RR7 -> RIPCOM Provider Adapter -> RIPCOM Provider Runtime -> Eclipse Serpent

Fluxo futuro de outra plataforma:

OUTRA PLATAFORMA -> RIPCOM B2B API -> sessão -> launch URL -> PLAYER RIPCOM

A plataforma parceira não recebe o código-fonte do motor do jogo nem acesso ao banco da RIPCOM.

6. API B2B RIPCOM
======================================================================

Edge Function pública:
ripcom-b2b

Base URL atual do sandbox:
https://tndnqjbkfwongolorvjm.supabase.co/functions/v1/ripcom-b2b

IMPORTANTE:
A função ripcom-b2b usa verify_jwt=false intencionalmente.
Ela não usa o login do RR7 como autenticação B2B.
A autenticação externa é feita por assinatura RSA do operador.

------------------------------
6.1 ENDPOINT DE SAÚDE
------------------------------

GET /v1/health

Serve para verificar se a API RIPCOM está online.

Não precisa de assinatura de operador.

Retorna informações como:
- provider = RIPCOM
- status = ok
- api = v1
- mode = DEMO

------------------------------
6.2 CATÁLOGO DE JOGOS
------------------------------

GET /v1/games

Retorna somente os jogos que foram liberados para o operador autenticado.

Exemplo:
um operador pode receber Eclipse Serpent, enquanto outro futuramente pode receber 5 jogos diferentes.

A liberação é controlada pela tabela ripcom_operator_games.

------------------------------
6.3 CRIAR SESSÃO
------------------------------

POST /v1/sessions

Cria uma sessão RIPCOM para um jogador pertencente à plataforma parceira.

Payload principal:
- game_code
- player_id
- starting_balance no sandbox

Exemplo de game_code:
ripcom-slot:eclipse-serpent

A resposta contém:
- session_id
- session_token
- status
- currency
- balance
- expires_at

------------------------------
6.4 GERAR LAUNCH URL
------------------------------

POST /v1/games/launch

Recebe session_token e devolve launch_url.

A launch URL abre o player independente da RIPCOM.

A plataforma pode usar essa URL em:
- iframe
- redirect
- webview compatível

------------------------------
6.5 ENCERRAR SESSÃO
------------------------------

POST /v1/sessions/close

Encerra a sessão RIPCOM correspondente ao token informado.

------------------------------
6.6 WALLET REAL
------------------------------

Rotas /v1/wallet/* ainda NÃO estão habilitadas para dinheiro real.

No sandbox a RIPCOM utiliza saldo DEMO interno por sessão.

A API responde DEMO_ONLY_INTERNAL_WALLET quando uma rota de wallet real é chamada.

Isso é intencional para manter dinheiro real completamente separado da fase atual.

======================================================================
7. AUTENTICAÇÃO B2B RSA
======================================================================

Cada operador deve ter um par de chaves RSA 2048.

A plataforma parceira mantém:
PRIVATE KEY

A RIPCOM armazena:
PUBLIC KEY

A chave privada nunca deve ser enviada para a RIPCOM.

Headers obrigatórios da API assinada:

X-Ripcom-Operator
X-Ripcom-Timestamp
X-Ripcom-Request-Id
X-Ripcom-Signature

Assinatura:
RSA-SHA256 / RSASSA-PKCS1-v1_5

Payload canônico:

METHOD\nPATH\nTIMESTAMP\nREQUEST_ID\nSHA256_HEX(BODY_EXATO)

O timestamp possui janela de tolerância para reduzir ataques de replay.

O request ID também é usado para idempotência.

======================================================================
8. IDEMPOTÊNCIA
======================================================================

Tabela:
public.ripcom_api_requests

Função:
evitar processar duas vezes a mesma requisição B2B.

Chave lógica:
operator_id + request_id

Se a mesma requisição for repetida exatamente:
a RIPCOM pode devolver a resposta armazenada anteriormente.

Se o mesmo request_id for reutilizado com método, rota ou body diferente:
retorna IDEMPOTENCY_CONFLICT.

Isso protege criação de sessão e futuras transações contra duplicação acidental.

======================================================================
14. EDGE FUNCTION ripcom-provider
======================================================================

Nome:
ripcom-provider

Função:
servir como runtime interno da RIPCOM quando o RR7 executa jogos da provedora diretamente.

Ela valida se:
- o jogo pertence à RIPCOM
- o provider é REAL
- a sessão é válida

Depois encaminha a ação para o motor correto.

Esse runtime interno é diferente da API pública ripcom-b2b.

ripcom-provider = integração interna RR7/RIPCOM
ripcom-b2b = integração externa para parceiros

26. SEGURANÇA
======================================================================

Regras obrigatórias:

1. Nunca colocar private key RSA no frontend.
2. Nunca salvar private key de parceiro no banco RIPCOM.
3. RIPCOM armazena somente public keys.
4. Cada operador deve usar chave própria.
5. Requests assinados possuem timestamp.
6. Requests usam request ID único.
7. Idempotência evita duplicações.
8. Player recebe somente token temporário de sessão.
9. Banco possui RLS para registros administrativos.
10. Função de liquidação DEMO é restrita ao service_role.
11. Produção de dinheiro real não deve ser ativada apenas mudando um campo de configuração.

28. O QUE É SANDBOX E O QUE É PRODUÇÃO
======================================================================

SANDBOX:
- modo atual
- somente DEMO
- saldo fictício
- usado para integração técnica
- usado para homologação de parceiros

PRODUCTION:
- estrutura prevista no cadastro
- NÃO significa que dinheiro real esteja autorizado
- não deve ser habilitada comercialmente sem requisitos técnicos, jurídicos, regulatórios e certificações aplicáveis

======================================================================
29. O QUE AINDA NÃO É PRODUÇÃO COMERCIAL
======================================================================

Ainda não considerar pronto para operação comercial de dinheiro real:

- wallet real
- callbacks financeiros reais
- certificação independente do RNG
- certificação matemática dos jogos
- compliance específico por jurisdição
- gestão formal de releases de jogos
- SLA comercial
- infraestrutura dedicada de domínio próprio
- WAF/rate limiting de produção
- rotação automática de chaves
- portal separado em domínio RIPCOM próprio

Esses itens devem ser implementados como fases próprias.

30. PRÓXIMOS PASSOS RECOMENDADOS
======================================================================

Fase seguinte recomendada:

1. Validar portal RIPCOM e SDK no CI.
2. Criar um segundo operador sandbox de teste usando o painel.
3. Gerar RSA desse operador.
4. Rodar smoke test completo da API B2B.
5. Validar launch do Eclipse Serpent fora do fluxo normal do RR7.
6. Criar versionamento formal dos jogos RIPCOM.
7. Criar Game Manifest por jogo.
8. Criar segundo jogo autoral usando o mesmo runtime/API.
9. Preparar domínio próprio da RIPCOM quando houver domínio definido.
10. Criar ambiente staging separado do RR7 antes de aceitar parceiro externo real.
